# 数学建模工作流

本 skill 是数学建模竞赛项目的总控入口。它不替代后续阶段 skill，而是负责启动流程、询问偏好、记录决策、生成计划，并按顺序调用各阶段 skill。

## 数学建模规范参考

如需领域判断，读取 `../_references/math_modeling_norms.md`。同时读取 `../_references/workflow_gate_protocol.md`，把逐题软画像、推导先行、六项检查、红队测试、模型深度和数据溯源嵌入现有阶段。两份参考文件都不改变本 skill 的阶段顺序和产出约定。

必须读取 `../_references/workflow_state_protocol.md`。`todo.md` 面向用户，`workflow_state.json` 用于机器恢复、门禁和产物登记。

## 必须产出

在当前工作目录中创建或更新以下文件：

- `plan.md`：整体流程方案、建模方向、阶段顺序、预期产物和风险控制。
- `todo.md`：具体待办事项列表，记录每个阶段的任务和状态。
- `workflow_state.json`：机器可读的阶段、问题、门禁、产物和未解决事项。

## 工作流

### 1. 询问用户偏好 AskUserQuestions

在规划前，只询问会实质影响流程的问题。问题要少而关键。

优先询问（按重要性排序）：

1. **排版引擎**：Typst 还是 LaTeX？— 决定 5writing 使用哪套模板和编译命令。两套引擎均覆盖全部模板（14 中 + 3 英）。Typst 使用 `typst` 命令编译；LaTeX 使用 `xelatex` 命令编译（需跑两遍解决交叉引用）。
2. **竞赛类型**：国赛/华为杯/华中杯/MCM/...— 决定模板选择，见 5writing 的模板族清单。
3. **论文语言**：中文/英文 — MCM/ICM/COMAP 强制英文，其他默认中文。
4. **子问题数量是否已知**：影响章节文件生成数量。若未知，由 2analysis-modeling 阶段根据题面确定。

将用户的选择记录到 `plan.md` 的"方案"小节中。

随后初始化状态文件；已存在时读取并恢复，不得覆盖：

```bash
python "<项目根>/backend/scripts/workflow_state.py" init
python "<项目根>/backend/scripts/workflow_state.py" show
```


### 2. 制定方案

按以下结构编写 `plan.md`：

```markdown
# 方案

要依次调用这些 skill，按照里面要求完成任务。

用户偏好：
- 排版引擎：<Typst / LaTeX>
- 竞赛类型：<国赛 / 华为杯 / MCM / ...>
- 论文语言：<中文 / 英文>
- 子问题数量：<已知 N 个 / 待分析确定>

workflow:
   1. 全局分析   - 拆题、逐题机理/数据/优化软画像、分层知识库检索（2analysis-modeling 第一阶段）
   2. 逐题求解   - 对每个子问题：建模→推导门→编码→红队验证→记录，下一题建模时参考前面结果
   3. 流程图     - `4drawio`
   4. 论文撰写   - `5writing`（拿到全部结果后统一写作）
   5. 验证验收   - `6verity`
```

**关键原则**：建模和编码不分离，但代码必须通过推导门后再实现。每个子问题先形成可求解推导并完成六项检查，再跑代码和至少 3 类红队测试；确认模型可行后再做下一题。这样下一题可以直接引用上题的真实结果，保持连续性。

## 项目目录结构

各阶段按此骨架创建和填充文件：

```text
.
├── plan.md                      # 1: 本文件
├── todo.md                      # 1: 待办事项
├── workflow_state.json          # 1-6: 机器可读状态与门禁
├── analysis/                    # 1+2: 可审计推导与建模门禁
│   └── derivations.md           #     逐题推导、可求解形式、六项检查
├── data/                        # 1+2: 题面附件、外部数据与来源登记
│   └── SOURCES.md               #     数据/参数来源、许可边界、用途
├── reports/                     # 各阶段文档报告
│   ├── ANALYSIS_MODELING_REPORT.md  # 1: 赛题分析-建模报告（2analysis-modeling）
│   ├── RESULTS_REPORT.md            # 2: 结果报告（3coding-visual）
│   ├── DRAWIO_REPORT.md             # 3: 非数据图说明（4drawio）
│   ├── VERIFY_REPORT.md             # 5: 验收报告（6verity）
├── code/                        # 2: 代码（3coding-visual）
│   ├── problem1.py
│   ├── problem2.py
│   ├── problem3.py               # 问题的数量应该更具题目动态调整
│   ├── ...
│   └── utils.py
├── results/                     # 2: 结果记录（3coding-visual）
├── figures/                     # 2+3: 所有图表（3coding-visual + 4drawio）
│   ├── *.pdf                    #     数据图 + 非数据图 PDF
│   ├── *.drawio                 #     非数据图源文件
├── paper/                       # 4: 论文（5writing）
│   ├── main.typ / main.tex      #     论文主文件（按用户选择的引擎）
│   └── sections/                #     各节文件（.typ 或 .tex）
```

方案必须明确每个阶段由哪个下游 skill 负责，以及该阶段应产出什么文件。

### 3. 生成待办

将 `todo.md` 写成阶段性 checklist，格式如下：

```markdown
# 待办事项

- [ ] 1. 全局分析 - 拆题 + 逐题软画像 + 分层知识库检索 + 来源登记
- [ ] 2. 问题一 - 建模 → 推导/六项检查 → 编码 → 红队验证
- [ ] 3. 问题二 - 建模（参考问题一结果）→ 推导/六项检查 → 编码 → 红队验证
- [ ] 4. 问题三 - 建模（参考前两题结果）→ 推导/六项检查 → 编码 → 红队验证
- [ ] 5. EDA + 敏感性分析 - 建模 → 编码
- [ ] 6. 流程与架构图绘制 - `4drawio`
- [ ] 7. 竞赛论文撰写 - `5writing`（全部结果就绪后统一写作）
- [ ] 8. 验证和验收 - `6verity`
```

> 子问题数量按实际题目调整。每完成一个阶段，更新对应任务状态。

### 4. 依次执行阶段

按以下顺序执行，**注意阶段 2+3 的逐题求解是核心改进：建模和编码不分离，每个子问题建完模立刻跑代码验证**。

| 阶段 | Skill | 说明 |
|------|-------|------|
| 全局分析 | `2analysis-modeling`（第一阶段） | 拆解所有子问题、记录机理/数据/优化软画像、检索证据案例和方法卡、完成数据理解与来源登记。产出可修订的初步建模方向。 |
| 逐题求解 | `2analysis-modeling`（第二阶段）+ `3coding-visual` 交替 | **对每个子问题**：详细建模 → 写入推导与可求解形式 → 六项检查 → 编码求解 → 常规验证与至少 3 类红队测试 → 记录。**上一题的真实结果直接传给下一题的建模阶段**。 |
| 流程图 | `4drawio` | 全部求解完成后，统一绘制方法流程图、架构图等非数据图示。 |
| 论文撰写 | `5writing` | **拿到全部问题的建模方案和结果后**，从头到尾一次性撰写论文，确保各章节能前后呼应、符号统一。 |
| 验证验收 | `6verity` | 完整检查论文结构、数值一致性、编译和提交就绪。 |

**逐题求解的执行细节**（阶段 2+3 的核心）：

```
对每个子问题 i (i=1,2,3...):
  ┌─ 建模 ─────────────────────────────────────────┐
  │  参考知识库中匹配的决策卡片                      │
  │  如果 i>1，主动引用前面子问题的真实结果           │
  │  明确写清：本问题如何依赖/延伸上一问题的结论       │
  │  写入 derivations.md：推导、可求解形式、六项检查    │
  │  产出：该子问题的建模方案和通过记录                 │
  └────────────────────────────────────────────────┘
                      ↓
  ┌─ 编码 ─────────────────────────────────────────┐
  │  实现该子问题的模型和算法                        │
  │  跑出结果 → 验证约束 → 至少 3 类红队测试 → 生成图表 │
  │  用 print() 输出数据特征供后续写作使用            │
  │  产出：代码、图表、结果记录                       │
  └────────────────────────────────────────────────┘
                      ↓
  ┌─ 验证 ─────────────────────────────────────────┐
  │  完成清单、红队证据和模型深度记录                 │
  │  结果数值合理？与上一问可衔接？                   │
  │  通过后 → 进入下一子问题                         │
  └────────────────────────────────────────────────┘

全部子问题完成后：
  → EDA 分析 + 敏感性分析（同样建模→编码）
  → 标记所有问题求解完成
```

**为什么这样做而不是全部建模完再编码**：

1. 建模方案是否可行，只有跑完代码才知道。逐题验证避免"全盘推翻"。
2. 问题二/三往往依赖问题一的结果。拿到真实数值后才能准确建模。
3. 编码中发现的数据问题（缺失、异常、维度不匹配）可以立即反馈到下一题的建模。
4. 论文写作时所有结果已就绪，前后符号和结论自然统一。

## 阶段边界

- `3coding-visual` 负责生成所有依赖计算结果或实验输出的数据图表。
- `4drawio` 只负责概念图、算法流程图、架构图、路线图等非数据型图示。
- 不要让 `4drawio` 重复绘制 `3coding-visual` 已经生成的统计图或数据图。
- `5writing` 负责决定图表在论文中的位置，并按所选引擎写入图表代码：
  - Typst：`#figure(image("../../figures/xxx.pdf", width: 85%), caption: [...])`
  - LaTeX：`\begin{figure}[H]\centering\includegraphics[width=0.85\textwidth]{../../figures/xxx.pdf}\caption{...}\label{fig:xxx}\end{figure}`
- 不要让 `5writing` 编造数值结论。论文中的数值必须来自 `RESULTS_REPORT.md`、结果表或已生成图表的数据。
